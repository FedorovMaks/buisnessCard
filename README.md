# Digital Card API

Цифровая визитка в виде GraphQL API: профиль, ссылки, навыки, опыт работы и проекты.

**Стек:** TypeScript · Node.js 24 · NestJS 12 · GraphQL (Apollo Server 5, code-first) · Prisma 7 · PostgreSQL 18 · Docker

## Быстрый старт

```bash
docker compose up --build
```

После старта откройте Apollo Sandbox: <http://localhost:3000/graphql>.

При запуске контейнер сам применяет миграции (`prisma migrate deploy`), заполняет базу данными визитки и только после этого поднимает HTTP-сервер. Ничего вручную делать не нужно.

Если порты 5432 или 3000 уже заняты, их можно переопределить: `POSTGRES_PORT=5434 API_PORT=3001 docker compose up --build`.

### Пример запроса

```graphql
query {
  profile {
    name
    headline
    description
    links {
      label
      url
    }
    skills {
      name
      category
    }
    experience {
      company
      position
      achievements
      period {
        startDate
        endDate
        isCurrent
        durationInMonths
      }
    }
    projects {
      name
      url
      repositoryUrl
      technologies {
        name
      }
    }
  }
}
```

## Локальная разработка

Нужен Node.js ≥ 22.12 (этого требуют Prisma 7 и NestJS 12).

```bash
cp .env.example .env
docker compose up -d db
npm install
npm run db:deploy
npm run db:seed
npm run start:dev
```

| Скрипт                               | Назначение                                                     |
| ------------------------------------ | -------------------------------------------------------------- |
| `npm run start:dev`                  | dev-сервер с hot reload, генерирует `schema.gql`               |
| `npm run build`                      | генерация Prisma Client и сборка в `dist/`                     |
| `npm run start:prod`                 | миграции → сид → запуск собранного приложения                  |
| `npm run db:migrate`                 | создать новую миграцию после изменения `schema.prisma`         |
| `npm run db:seed`                    | перезаполнить базу из `src/database/seed/data/profile.data.ts` |
| `npm run typecheck` / `npm run lint` | проверка типов и линтер                                        |

Данные визитки лежат в одном файле: [`src/database/seed/data/profile.data.ts`](src/database/seed/data/profile.data.ts).

## Архитектурные решения

### Модули по доменам и три слоя

Каждый домен (`profile`, `skill`, `experience`, `project`) — отдельный Nest-модуль с одинаковой внутренней структурой:

- **Resolver** — только GraphQL: объявляет поля и делегирует. Не знает о Prisma и SQL.
- **Service** — бизнес-логика и публичный API модуля для остального приложения. Например, `ProfileService` решает, что отсутствие профиля — это ошибка `NOT_FOUND`, а `ExperienceService` вычисляет период работы.
- **Repository** — единственное место, где пишутся запросы к базе.

Сервисы бросают стандартные исключения Nest (`NotFoundException` и т. п.) и ничего не знают о GraphQL. Перевод в GraphQL-ошибку с кодом (`NOT_FOUND`, `BAD_REQUEST`, …) без утечки внутренних деталей делается в одном месте — `src/graphql/format-error.ts`.

Для `skill` и `project` сервис сейчас почти прозрачный, но слой оставлен намеренно: резолверы и загрузчики зависят от сервисов, а не от хранилища, поэтому любую логику (фильтрацию, кэширование, правила видимости) можно добавить без изменения GraphQL-слоя.

### Code-first GraphQL

Схема строится из TypeScript-классов (`models/*.model.ts`), поэтому типы API и кода не расходятся. GraphQL-модели описывают публичный контракт и намеренно не совпадают с таблицами один в один: служебные поля (`profileId`, `sortOrder`) наружу не попадают, а вычисляемые (`Experience.period`) существуют только в API. В dev-режиме схема выгружается в `schema.gql`, её удобно смотреть на ревью.

### Вложенные данные и проблема N+1

Связанные поля (`Profile.skills`, `Profile.projects`, `Project.technologies` и т. д.) резолвятся через [DataLoader](https://github.com/graphql/dataloader). Загрузчик собирает все ключи, запрошенные на одном уровне дерева, и делает **один** запрос `WHERE id IN (...)`. В итоге число SQL-запросов зависит от глубины запроса, а не от количества записей. Например, запрос `profile { projects { technologies { name } } }` выполняет 4 SQL-запроса (профиль, проекты, связи проект–навык, навыки) при любом количестве проектов. Без батчинга было бы 2 + 2N.

Детали реализации:

- Загрузчики создаются **на каждый запрос** в фабрике GraphQL-контекста (`LoadersFactory.create()`). Так кэш DataLoader не протекает между пользователями. При этом резолверы и сервисы остаются синглтонами. Альтернатива — `Scope.REQUEST` в DI Nest — пересоздавала бы всю цепочку провайдеров на каждый запрос.
- `createGroupedLoader` — одна обобщённая функция для всех связей «один ко многим»: группирует плоский результат по внешнему ключу и возвращает массивы в порядке ключей, как требует контракт DataLoader.
- Запрашиваются только те связи, которые клиент реально выбрал в запросе: если `projects` нет в запросе, к таблице проектов никто не обращается.

Почему не `include` по selection set (разбор `info` и построение одного запроса с JOIN): такой подход плотно связывает GraphQL-слой со структурой Prisma-запроса, плохо переносит вычисляемые поля и ломается на фрагментах и алиасах. DataLoader — стандартное, предсказуемое решение, которое не зависит от формы запроса.

### Модель данных

- Таблицы нормализованы, у всех связей с профилем стоит `ON DELETE CASCADE`.
- Порядок вывода задаётся явным полем `sortOrder` (уникальным внутри профиля), а не порядком вставки, на который в SQL полагаться нельзя. Опыт работы сортируется по дате начала.
- Связь проектов и навыков — многие ко многим через `project_technologies` с собственным `sortOrder`: технологии проекта ссылаются на навыки из профиля, а не дублируются строками.
- Достижения хранятся как `text[]`: это упорядоченный список строк без собственной идентичности, отдельная таблица была бы лишним JOIN без выгоды.
- Даты хранятся как `DATE`, не `TIMESTAMP`: для периода работы время суток не имеет смысла. Наружу они отдаются собственным скаляром `Date` в формате `YYYY-MM-DD`.
- Первичные ключи — UUID v7: не раскрывают количество записей и при этом монотонны, что хорошо для B-tree индексов.
- Индексы покрывают реальные запросы загрузчиков: `(profile_id, sort_order)` и `(profile_id, start_date DESC)`.

### Инициализация и заполнение базы

Старт контейнера: `prisma migrate deploy` → `node dist/seed.js` → `node dist/main.js`. Если миграция или сид падают, приложение не стартует — сервис никогда не работает на неподготовленной базе.

- **Миграции** лежат в репозитории и применяются через `migrate deploy`: это детерминированно и безопасно для продакшена, в отличие от `db push`.
- **Данные** описаны в типизированном TS-файле и перед записью проверяются Zod-схемой: корректность URL и дат, `endDate ≥ startDate`, уникальность навыков, ссылки технологий проектов только на существующие навыки. Ошибка в данных останавливает деплой с понятным сообщением, а не превращается в битую запись.
- **Идемпотентность.** Источник истины — файл с данными, база — его проекция. Поэтому сид при каждом запуске заменяет профиль целиком в одной транзакции. Правки в файле попадают в базу после передеплоя, повторные запуски безопасны, а «осиротевших» записей не остаётся (с upsert их пришлось бы вычищать отдельно).
- **Конкурентный запуск.** Транзакция берёт `pg_advisory_xact_lock`, поэтому при одновременном старте нескольких реплик сиды выполняются по очереди, а не конфликтуют.
- Сидинг — отдельный процесс, а не хук в приложении: HTTP-серверу не нужны права и код на запись, а сид можно запустить независимо (`npm run db:seed`).

### Конфигурация

Переменные окружения валидируются Zod-схемой при старте (`src/config/env.ts`). Приложение падает сразу с понятной ошибкой, если, например, нет `DATABASE_URL`. Типизированный `ConfigService<Env, true>` исключает опечатки в ключах.

### Платформа

- Проект собран как **ES-модули**: NestJS 12 распространяется только в ESM.
- Prisma 7 работает без Rust-движка через driver adapter `@prisma/adapter-pg`. Клиент генерируется в `src/generated` и в репозиторий не коммитится.
- Docker-образ multi-stage: dev-зависимости удаляются через `npm prune --omit=dev`, процесс работает от непривилегированного пользователя `node`, а `exec` делает Node.js PID 1, чтобы он корректно получал `SIGTERM`.

## Что можно развить

- Ограничение глубины и сложности запросов (актуально для публичного API без авторизации).
- Unit-тесты доменной логики (`toEmploymentPeriod`, валидация сид-данных) и e2e-тесты GraphQL на Testcontainers.
- HTTP-кэширование ответа: данные меняются только при деплое.
